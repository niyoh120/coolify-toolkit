# 运维手册

## 部署

1. 准备 `.env`（参考 `.env.example`）：`COOLIFY_BASE_URL`、`COOLIFY_API_KEY`、`PUBLIC_ORIGIN` 必填。
2. 强烈建议配置 `EXCLUDED_RESOURCE_UUIDS`：Coolify 自身、数据库、监控等一切非目标资源；类型识别（build_pack）之外的兜底。
3. `docker compose up -d --build`。容器以非 root 运行，仅写 `/data`。
4. Traefik 路由必须挂认证中间件（basicAuth / forwardAuth），覆盖 UI 与 `/api/*`；确认没有旁路端口（compose 未发布任何宿主端口）。
5. 调度配置（同步/检查周期、时区）存于数据库，UI 修改即生效；环境变量 `SYNC_CRON`/`CHECK_CRON`/`CRON_TIMEZONE`/`SERVER_PLATFORM` 已移除。部署并发默认 1（`DEPLOY_CONCURRENCY`）；toolkit 对单资源串行提交，调高前先确认 Coolify 队列与节点负载。鉴权由 Traefik 承担，toolkit 无内置账户，凭据仅驻留服务端。
6. 首次打开 UI → 设置 → 测试 Coolify 连接 → 资源页「重新同步」。

## 上线建议顺序

1. 全部资源保持「忽略」，观察同步结果（列表、当前镜像、外部变更标记）。
2. 逐个为要接管的资源设置追踪 tag 与目标平台，切「通知」或「手动」策略。
3. 点「立即检查」或等定时扫描：首次检查会自动创建初始化任务、固定摘要并部署（Application 会有 deployment 证据），先在小范围确认结果。
4. 稳定后个别资源再切「自动更新」。避免一上来全量自动。

## 资源页与服务操作

- 资源页分「应用」「服务」两个 Tab；服务 Tab 按 Compose 服务分组，默认展开，可一键折叠/展开全部（显示模式，与筛选、翻页无关；单组箭头为局部例外，切换全局模式时重置），按组分页（10/20/50/100 组，默认 20）。组头汇总（有更新 / 待配置受阻）来自子容器，父级运行状态单独标注。
- 服务名进入服务详情：聚合该服务全部 active 子容器，支持 **整组检查 / 整组提交更新 / 批量策略**。范围是当前 active 快照，确认弹窗列出资源与跳过原因；执行中串行逐项发起，展示进度与逐项结果。
- 整组更新沿用单资源任务路径：每个子容器独立建任务，HTTP 202 仅表示任务已提交；部分失败继续。同服务前一个任务在等待自动检查时，其余任务排队。
- **确认更新完成**：Compose 子容器提交后默认等待约 60 秒做一次运行状态检查（到期后由 5 秒 worker tick 触发，实际时刻受负载影响）；容器主状态为 running 且子容器 image 与 raw compose 目标节点均等于候选引用即推定成功（`lastSuccessSource=runtime_observation`），解除确认阻塞并放行同服务后续任务。也可在服务 Tab 行内点「确认更新完成」提前确认；勾选后可用「批量确认更新完成」，范围是弹窗时冻结的任务快照，逐项反馈已确认/跳过/失败。
- **静默失败边界**：若更新后容器仍在 running（例如启动后崩溃被重启、上游进程守护拉回旧容器），运行观察会推定成功；同一摘要的后续检查通常保持 matching，直到上游出现新摘要再继续更新。这是简单单次检查的已知边界，通知与日志会标注“运行观察自动确认”。
- 升级兼容：旧版本遗留的 running/待确认 Compose 任务在启动时按 `updatedAt+60 秒` 补齐到期时间并由 worker 接管；关联的未发送“待人工确认”提醒会被暂停并标注原因，已发送的历史通知保留。全局暂停期间已提交任务的自动检查继续，只有新部署被阻止。
- 批量策略只作用于子容器；父服务策略保持不变，被排除/外部修改子容器的安全约束不变。
- 列表页批量操作范围 = 当前页筛选后的选择集（含折叠组）；与服务详情的整组范围独立，请按文案区分。
- 子容器平台继承父服务节点；历史遗留的空平台会在下一次完整同步时自动恢复（compose/手动平台保留）。发现服务子容器大面积「目标平台待配置」时，点一次「重新同步」即可自愈，无需逐个手动设置。

## 备份与升级

- 业务数据（SQLite + WAL）在 `/data`。升级/迁移前：停止容器 → 备份整个目录（含 `toolkit.db-wal`、`toolkit.db-shm`、`toolkit.lock.db`）→ 再升级。
- 迁移失败（启动日志 `startup failed`）时回滚到上一镜像并恢复备份目录。
- 单实例锁：`/data/toolkit.lock.db`（SQLite 内核级文件锁，锁随进程退出由内核自动释放，kill -9 / 断电后重启可直接启动；若锁提示存在活跃实例，先确认无重复容器或共享同一数据卷的其它实例）。若启动报 `lock file ... is corrupt (not a SQLite database)`，说明锁文件损坏（非 SQLite 格式），停止容器删除该文件后重启即可，锁状态完全由内核持有，删除无副作用。

## 旧库升级（管理分类迁移）

自本版本起，资源记录区分「管理分类」状态（`management_classified`）与结构化镜像问题（`image_issue`），用于取代旧版把配置排除与镜像解析失败合并写入 `excluded_infra` 的历史语义。

**升级机制**：完全经现有 `db migrate`（版本化 Drizzle SQL migration，`drizzle/20261001000000_management_classification`）执行。启动顺序保持 `loadConfig → migrate → buildDeps → reconcileOnBoot → scheduler.start → HTTP`；应用代码内没有一次性重分类或回填逻辑，迁移由迁移历史控制只执行一次，日常重启不会重新分类。

**升级后的首次同步窗口**（旧库存量记录全部 `managementClassified=false`）：

1. 所有存量资源显示「待同步确认」，默认可见、配置只读；排除/受管/候选统计排除它们，`resourcesTotal` 口径说明「含服务父记录、已排除及待同步确认资源」。
2. 策略/配置保存、预览、新任务与重试返回 409；普通检查返回 blocked/待同步确认；自定义 cron 暂缓注册。
3. 未提交部署的排队任务保持 pending，等同步后重新判定；已提交部署（有 deployment UUID）的任务继续证据恢复（仅查询/poll，无新 PATCH/start）。已提交 Application 的证据查询与 Compose 人工确认继续可用。
4. **完成一次「重新同步」后**：成功刷新的记录转为明确分类，策略与调度按原配置恢复；部分失败记录继续待确认，修复后下次同步再确认。历史 removed 记录可能长期保留待确认，仅展示历史，不影响运行。
5. 镜像异常记录（gcr.io 等）同步后显示具体原因并保持只读；修复镜像后同步自动清除。

**修改排除名单的标准步骤**：暂停自动更新 → 修改 `EXCLUDED_RESOURCE_UUIDS` → 重启 → 「重新同步」→ 核对分类结果 → 恢复自动更新。名单变更经由配置加载与正常同步更新投影，日常重启不会全库重分类。

**实机验收**：待验收（需获授权只读访问真实实例；核对新版实例同步完成后的镜像异常原因、只读控件与统计口径，并记录实例版本与验收时间。不可访问/新版未部署/尚未同步时保持本标注）。

**回滚**：升级后经正常同步的 `excluded_infra` 已收敛为纯配置排除语义；单独回滚旧镜像会忽略镜像问题。请配套回滚（旧镜像 + 升级前数据库备份）。若升级后已有外部部署，先保全新库与部署记录、暂停自动更新并对账，确认目标一致后再恢复调度。

## 外部修改后的接管（采纳 / 保存恢复 / 重置）

绕过 toolkit 在 Coolify 手动改镜像后，同步会把资源置为「外部修改，需重新确认」并保持旧基线；自动同步、定时检查与自动更新都会尊重该阻塞。恢复管理有三个入口（资源详情页「恢复管理」卡片），全部经一次预览 + 一次确认：

**1. 采纳当前镜像并更新**（推荐路径）

- 预览只读：读取 Coolify 实时配置、解析新追踪渠道（默认取现场 tag；可填写显式 tag 覆盖）、解析该渠道当前上游摘要，展示原渠道、实时配置、将采用的渠道、目标完整引用与影响范围，并签发 10 分钟有效的采纳 token。
- 确认后一次性落库：切换渠道、把实时配置记为新基线、清旧观察与成功投影（采纳本身不产生部署证据）、递增追踪版本，并创建一条普通任务按既有执行器部署。
- 浮动 tag 现场（如 `:latest`）的基线先记为带 tag 引用、摘要待任务确认（任务为初始化类型）；digest-pinned 现场且摘要已等于目标时仅采纳、不部署（返回 skipped）。
- 纯摘要现场无法反推 tag：同仓库会沿用旧 tag 供确认；换仓或旧 tag 为空时必须填写 tag。

**2. 保存追踪配置（外部修改状态下）**

- `external_change` 状态下修改来源 tag 保存时，toolkit 会先读取 Coolify 实时配置并采纳为已确认基线，再更新渠道；Coolify 暂时不可达时保存拒绝且所有字段保持原值。
- 普通修改 tag（非阻塞状态）保留已确认基线与真实成功证据，只清旧渠道观察；改追踪 tag 后即使当前配置仍是旧 tag，也能以原配置为 prior 更新。
- 把更新来源指向与现场不同的仓库属于镜像迁移，会被拒绝并提示先在 Coolify 修改。

**3. 重置追踪并忽略**（兜底）

- 纯本地操作，Coolify 不可达时仍可执行：原子地把策略置为「忽略」、清空追踪账本（基线、观察、成功证据投影）、保留追踪 tag/平台/cron、Coolify 配置与任务历史。
- 忽略下不检查、不初始化、不自动部署；旧任务的重试也服从忽略与版本检查。重新选择非忽略策略即可恢复管理；需要采用现场新 tag 时再用采纳流程。
- 镜像异常状态（如 unsupported_registry）下重置仍可用（缩小管理范围），待同步确认与已排除资源维持管理边界。

**并发与安全边界**

- 资源存在 pending/running（含等待确认）或任意 `unknown_submit` 任务时，采纳与重置返回 409 并附任务 ID；Compose 操作同时检查同一父服务下的在途任务。
- 每条追踪行持有持久 `trackingRevision`（迁移默认 0）：来源/平台修改、采纳、重置都会递增；预览 token、在途任务与异步观察都绑定版本，旧结果到达时被丢弃或转为 `tracking_changed` 冲突，历史任务保留但不会写入。
- 预览 token（更新与采纳）单次使用，在提交事务内删除；事务失败可重试同一 token，过期 token 在签发时有界清理（仅限预览元数据）。

**回滚要点**：上线前备份 SQLite；升级后先在单个可控资源上验证采纳闭环。附加的版本列可留在库中（旧程序会忽略新守卫）；回退旧版本运行期间，建议将受影响资源保持「忽略」，并通过重新同步/人工核对确认基线。只有未发生新部署时才适合同时恢复旧库快照；已有新部署时保留新库与历史，避免配置与证据脱节。

## 失败处理（无回滚设计）

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 待同步确认 | 旧库升级后该记录尚未经正常同步分类 | 完成一次「重新同步」；期间配置只读、新管理动作暂停，排队任务保持等待 |
| 已排除（配置名单） | 自身或父服务命中 `EXCLUDED_RESOURCE_UUIDS` | 按上文标准步骤调整名单并同步；排除视图与详情直链可排查 |
| 暂不支持的镜像仓库：gcr.io 等 | 镜像 registry 在支持范围外（docker.io/ghcr.io/lscr.io） | 在 Coolify 改用受支持镜像或保持排除；修复后同步自动清除 |
| 镜像变量未解析 | Coolify 镜像引用含未展开变量（`$VAR`/`${VAR}`） | 核对 Coolify 实际镜像配置，修复后同步 |
| 镜像信息缺失 / 镜像引用无效 | Coolify 未返回镜像或引用格式非法 | 核对资源配置后同步 |
| 更新失败已暂停 | PATCH/部署/确认失败；目标配置保持写入值，上一成功证据保留 | 在 Coolify 排查（日志/健康），处理后点「同目标重试」；或在 Coolify 手工恢复后「重新同步」+「保存来源」解除阻塞 |
| 提交结果未知 | start 超时或响应无 deployment UUID 且历史无法唯一关联 | 先「更新历史」核对是否实际部署；绝不盲目重发。确认后用重试（会重新提交）或恢复同步 |
| 等待自动检查（Compose） | 已提交定向部署，等待延迟单次检查或人工确认 | 等待约 60 秒自动检查；也可在服务列表点「确认更新完成」提前确认。检查失败会转入「更新失败已暂停」并提供同目标重试 |
| 外部修改，需重新确认 | Coolify 中的镜像被 toolkit 之外修改 | 详情页「恢复管理」→「采纳当前镜像并更新」（推荐）；或在镜像追踪卡片修改追踪 tag 保存（会采纳现场为新基线）。旧基线在详情页完整展示 |
| 目标平台待配置 | 无可验证平台来源 | 在详情页填写 `os/arch[/variant]` |

## 通知

- Apprise 用持久配置模式：环境变量 `APPRISE_API_URL` + `APPRISE_CONFIG_KEY`（可选 `APPRISE_TAG`）。
- **`APPRISE_TAG` 何时必填**：apprise-api v2.0.0 的「公开/已锁定」访问模式拒绝无 tag 的有状态通知（HTTP 400），此时必须设置；「用户」模式或渠道全部未打标签时可省略。未设置时启动日志会给出提示。
- **非公开模式的认证**：「已锁定/用户」模式需要 HTTP Basic 凭据，配置 `APPRISE_PASSWORD`（服务端 `APPRISE_PASSWORD` 创建，`APPRISE_USER` 可选）后 toolkit 自动携带 `Authorization` 头；「公开」模式留空即可。凭据仅存服务端，设置页只显示"已配置认证"状态。
- 去重身份：事件类型 + 资源 + 候选摘要。重复检查不会重复入队。
- 重试：至多 3 次，指数退避，429 遵循 Retry-After；404/401/403 标记 paused 并在 UI 显示原因；至少一次语义，超时重试可能重复通知。
- Apprise 未配置时队列照常入队，配置后自动补发（或在通知页手动补发）。

## 排障

- **日志**：stdout JSON 行不打印任何凭据/原始外部响应；执行器进度存于任务 log。
- **Coolify 连接**：设置页「测试 Coolify 连接」；401 检查 token 权限（read/write/deploy）。
- **检查一直 blocked**：待同步确认 / 配置排除 / 镜像问题 / 忽略策略 / 无追踪 tag / 无平台 / 外部修改，检查结果会给出具体原因；详情页有对应徽章与说明。
- **子容器平台缺失**：节点未上报架构或历史缺陷遗留时，检查会以「目标平台待配置」跳过；节点恢复上报后一次完整同步自动回填。
- **429 / 限流**：检查器尊重 Retry-After 并保留旧观察；Docker Hub 匿名限流可在 `REGISTRY_CREDENTIALS_FILE` 配置只读凭据提升限额。
